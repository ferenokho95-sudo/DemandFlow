# Архитектура и решения

1. CLI или Airflow получает единую блокировку записи в SQLite `pipeline-lock.db`.
2. Содержимое CSV копируется в отдельную папку запуска. SHA-256 вычисляется по этим же байтам.
3. Проверяется контракт, строится таблица признаков из прошлых наблюдений.
4. Последние 14 дней всех товаров откладываются. Ridge обучается на предыдущих днях; прогноз на holdout выполняется рекурсивно. Seasonal naive повторяет неделю, также рекурсивно. Сравнение по MAE; WAPE не рассчитывается при нулевом знаменателе.
5. Победившая модель переобучается на всей истории, выдаёт прогноз на будущие даты. Если побеждает baseline, `model.joblib` содержит `model=None` и название стратегии.
6. Прогнозы прошлых запусков сопоставляются с появившимися фактическими наблюдениями. На каждую пару товар/дата берётся последний опубликованный прогноз. Это ретроспективная оценка, а не метрика качества будущих дат.
7. Полный режим синхронизирует внешние хранилища. После успешной синхронизации локальная транзакция добавляет прогнозы и переключает `active.run_id`.
8. API на каждый запрос читает актуальный run_id. Перезапуск API при публикации не требуется. API отдаёт уже рассчитанный пакетный прогноз; новые произвольные параметры модели в запросе не принимает.

SQL-витрина продаж PostgreSQL: ключ `(date, product_id)`. Витрина признаков сохраняется как CSV и копируется в MinIO. В ClickHouse ключ `(run_id,date,product_id)` разделяет версии; физические повторы при повторной доставке заменяются ReplacingMergeTree, при анализе используйте FINAL и нужный run_id.

### Почему без случайного train/test split

При прогнозировании случайное перемешивание переносит информацию из будущего в обучение. Здесь граница единая по календарю для всех товаров, а rolling-признаки используют только более ранние значения. При многошаговом прогнозе лаги дополняются предсказанными значениями.

### Почему одна задача Airflow

Для компактного проекта обучение и публикация образуют один управляемый запуск. Это упрощает блокировку и защиту активной версии. В крупной системе стадии следует разнести по задачам с явными URI артефактов и состояниями, а не передавать модель через XCom.

### Демонстрационные метрики и данные

Синтетические продажи имеют недельную сезонность, небольшой тренд и шум. Они нужны для проверки инфраструктуры. Высокое качество на них не доказывает качество на реальных продажах. В README не заявляются недостигнутые улучшения бизнеса или высокая нагрузка.
