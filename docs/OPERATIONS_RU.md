# Эксплуатация

## Проверка результата

`GET /ready` возвращает 200 после первого успешного расчёта; `/health` проверяет доступность процесса. `/report` показывает выбранную модель, MAE, WAPE, число строк, дату данных и алёрты. `/forecasts?product_id=SKU-001` возвращает прогноз для товара. `/metrics` отдаёт метрики Prometheus.

Пример запроса ClickHouse через контейнер:

```bash
docker compose exec clickhouse clickhouse-client --user demand --password click_local --query "SELECT * FROM forecasts FINAL ORDER BY date, product_id LIMIT 20"
```

Для сравнения версий добавьте `WHERE run_id='значение из /report'`. При изменённом пароле подставьте свой.

## Сбой и восстановление

Неуспешный запуск записывается со статусом `failed`; предыдущий опубликованный прогноз остаётся доступен. Исправьте данные или восстановите сервис, повторите расчёт. Одновременно выполняется один writer; конфликт блокировки завершает второй запуск ошибкой, Airflow повторяет попытку.

Жёсткое завершение процесса может оставить статус `running`. Блокировка SQLite освобождается ОС после закрытия процесса; перед повтором убедитесь, что старый процесс завершён. Контролируйте такие статусы при эксплуатации.

Внешние хранилища не участвуют в единой распределённой транзакции. Если ClickHouse или MLflow падает после записи PostgreSQL, остаются частичные внешние результаты, но API активную версию не меняет. Ориентируйтесь на опубликованный run_id и успешные запуски, а не на наличие произвольной папки S3. Для production нужны outbox/manifest, уборка незавершённых запусков и состояния публикации в центральной БД.

Повторный расчёт создаёт отдельную версию. Он не дублирует строки внутри опубликованного прогноза. История версий сохраняется намеренно. PostgreSQL-продажи заменяются транзакционно по полному CSV; это не CDC и не инкрементальная загрузка.

## Мониторинг

Prometheus собирает метрики раз в 15 секунд. Правила в `infra/alerts.yml` сигнализируют о недоступности API, неуспешном последнем запуске, устаревших данных и realized WAPE выше 30%. Алёрты видны в Prometheus. Отправка в почту/мессенджер не настроена; для неё понадобится Alertmanager и адрес назначения.

Время выполнения в отчёте охватывает локальный расчёт и создание артефактов, исключая синхронизацию внешних хранилищ. Логи идут в stdout контейнеров и логи Airflow. Нет обещаний по SLA/latency: нагрузочное тестирование этого стенда не выполнялось.

## Резервные копии

Сохраняйте `data/sales.csv`, Docker volumes PostgreSQL, ClickHouse, MinIO и state. Данные state содержат SQLite-реестр и локальные артефакты, в том числе MLflow. Для согласованной копии остановите writers и используйте штатный backup SQLite/БД. Не копируйте активный state.db отдельно от WAL.

`docker compose down` сохраняет volumes. `docker compose down -v` удаляет данные стенда; используйте только для осознанного полного сброса после резервного копирования.

## Перед production

Нужны авторизация, TLS, секреты, отдельные роли БД, мониторинг расписания/резервирования, центральный реестр публикаций, контроль ресурсов и зафиксированные образы по digest. Проверка модели должна включать несколько временных окон, дефициты, акции и правила бизнес-приёмки. Следует отделить загрузку данных, обучение и serving, настроить доставку реальных продаж и управляемый rollback версии.
